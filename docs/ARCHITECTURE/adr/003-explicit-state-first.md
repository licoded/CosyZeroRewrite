# ADR-003: 为什么先实现显式状态?

## 状态
有效

## 上下文
DFA 状态表示有两种主要方案：
1. **显式状态**: 每个状态是一个对象，显式枚举
2. **符号化状态 (BDD)**: 用 BDD 表示状态集合和转移关系

## 决策
**先实现显式状态**，BDD 符号化作为后续优化。

## 理由

| 方面 | 显式状态 | BDD 符号化 |
|------|---------|-----------|
| 实现复杂度 | 中等 | 高 |
| 调试难度 | 低 | 高 |
| 依赖 | 无 | CUDD/BuDDy |
| 适用规模 | n ≤ 15 变量 | n ≤ 100 变量 |
| 开发时间 | 2-3 天 | 1-2 周 |

**关键原因**:
1. **算法验证优先**: 先验证算法正确性
2. **快速迭代**: 显式状态更易调试和修改
3. **学习曲线**: BDD 库学习成本高
4. **性能瓶颈未明**: 不过早优化

## 实现对比

### 显式状态

```cpp
struct TableauState {
    std::unordered_set<Formula*> formulas;
    size_t hash;

    bool is_accepting() const;
    TableauState* next(Assignment) const;
};

// 每个状态是独立对象，显式存储
std::unordered_set<TableauState*> states_;
```

### BDD 符号化

```cpp
// 状态用 BDD 节点表示
BDD state_bdd;

// 转移关系是 BDD 函数
BDD transition_relation_;

// SCC 需要符号化算法
void symbolic_scc(BDD states);
```

## 后果

**正面**:
- 快速验证算法正确性
- 代码更易理解和调试
- 无额外依赖

**负面**:
- 状态空间指数爆炸 (n > 15 变量)
- 无法处理大规模问题

**风险**:
- 可能无法处理实际应用中的大规模公式
- 后续重构到 BDD 工作量大

**缓解**:
- 保留清晰的接口，便于后续替换实现
- 设计 `StateProvider` 抽象层

## 未来升级路径

```
当前 (显式状态)
    │
    ▼
抽象接口层 (IStateProvider)
    │
    ▼
┌───────────┬───────────┐
│ 显式实现  │  BDD 实现  │  ← 未来
└───────────┴───────────┘
```

## 何时升级到 BDD?

触发条件：
1. 实际问题规模超出显式状态能力
2. 性能分析显示状态构造是瓶颈
3. 有充足时间投入
